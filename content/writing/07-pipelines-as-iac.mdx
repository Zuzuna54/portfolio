title: Pipelines as infrastructure-as-code
date: "2026-09-08"

summary: A new pipeline shipped as a stack file and deployed without recompiling any service.

Most data pipelines are programs. You write one, you deploy the service that runs it, and adding a
pipeline means shipping the service again.

On one platform, pipelines were declared as infrastructure over custom resource types — a stream, an
indexing-and-query primitive, an agent. Not YAML config read at runtime: actual typed resources in
an infrastructure-as-code stack, planned and applied like any other.

A new pipeline is a stack file. It deploys without recompiling any backend service.

The consequence compounds. Because the query operations are declared on the resource, the platform's
gateway picks them up and exposes each as a tool automatically. So adding a pipeline also adds its
query surface, with no integration work at all.

The trade is that your primitives have to be right early. Resource types are an API, and changing
one after people have written stacks against it is a migration, not a refactor. We got the stream
and query primitives right and the agent primitive slightly wrong — it assumed a shape of work that
not every agent had.

Extending the system stopped requiring a deploy of the system. That is the whole prize.
